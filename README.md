## AmneziaWG = WireGuard + Obfuscation

요청하신 **"사용되는 IP가 외부에 알려지지 않도록"** 목표에 대해, 핵심은 아래와 같습니다.

- **WireGuard/AmneziaWG 자체만으로는 최종 출구(egress) IP를 완전히 숨길 수 없습니다.**
- 외부 서비스에는 결국 **출구 IP**가 보이며, 이를 숨기려면 구조적으로 우회 계층이 추가되어야 합니다.

### 권장 아키텍처

1. **클라이언트 → AmneziaWG 서버(중계 1단)**
   - DPI/패턴 탐지를 어렵게 만들기 위한 난독화 계층.
2. **AmneziaWG 서버 → NAT 게이트웨이 또는 프록시 풀(중계 2단)**
   - 실제 외부 통신은 2단 노드에서만 나가게 구성.
3. **로그 최소화 + 회전 IP 정책**
   - 고정 식별 위험을 줄이기 위해 egress IP/노드 로테이션 적용.

### 최대 우회 적용 방향 (실전 프로파일)

> 목표: 차단 회피 성공률 우선 + 원본 식별 최소화

- **2단 이상 고정**: `Client → AWG Relay-1 → Relay-2(Egress)`를 기본값으로 사용.
- **국가/ASN 분리**: Relay-1과 Relay-2를 서로 다른 사업자/대역으로 분리.
- **출구 IP 풀 운영**: 단일 egress 대신 다중 IP를 짧은 주기로 로테이션.
- **DNS 완전 터널링**: 클라이언트 DNS를 터널 내부로 강제(외부 DNS 직접 조회 차단).
- **IPv6 정책 일치**: IPv6 사용 시 Relay 전 구간 동일 보안정책, 미사용 시 비활성화.
- **Kill Switch 적용**: 터널 단절 시 평문 트래픽이 외부로 나가지 않게 차단.
- **로그 최소화**: 접속 성공/실패 카운터 수준만 보관, 원본 IP·세션 상세 로그는 최소화.
- **프로토콜 다변화**: 차단 패턴이 생기면 포트/전송경로/중계 노드 조합을 즉시 변경.

### 오픈된 VPN 서버 활용 가능 여부

결론부터 말하면 **기술적으로는 가능하지만, 권장하지 않습니다.**

- **신뢰 문제**: 오픈 VPN 운영자가 트래픽/메타데이터를 수집할 수 있습니다.
- **추적 위험**: 공용 서버는 다수 사용자가 섞여 이상 트래픽 감시·차단 대상이 되기 쉽습니다.
- **품질/지속성 문제**: 속도 저하, 잦은 차단, 구성 변경으로 서비스 안정성이 낮습니다.
- **보안 문제**: 악성 DNS 설정/인증서 위조/중간자 공격 시도 가능성을 배제하기 어렵습니다.

### 오픈 VPN을 꼭 써야 한다면 (최소 수칙)

- 개인 식별 계정 로그인(이메일/메신저/금융) 트래픽과 분리.
- VPN 내부 DNS를 신뢰 가능한 서버로 강제하고 누수 테스트 수행.
- 고정 사용 대신 단기 세션 중심으로 사용하고 민감 작업은 지양.
- 가능하면 **직접 통제 가능한 VPS 2대(중계/egress 분리)**로 대체.

### 운영 체크리스트

- VPN 서버의 공인 IP와 실제 egress IP를 분리했는가?
- DNS 누수 방지(DoH/DoT 또는 터널 내부 DNS 강제) 설정이 되었는가?
- IPv6 누수 방지(미사용 시 비활성화, 사용 시 동일 정책 적용) 되었는가?
- Kill Switch/방화벽 룰이 터널 장애 시에도 유지되는가?
- 서버/프록시 접근 로그에 원본 식별자가 과도하게 저장되지 않는가?
- 출구 IP 평판(블랙리스트/탐지율)을 주기적으로 확인하는가?

### 크로스플랫폼 가능 여부

가능합니다. **AmneziaWG는 운영체제 혼합 환경에서도 구성할 수 있습니다.**

- **클라이언트**: Windows / macOS / Linux / Android / iOS 조합 운영 가능.
- **서버(중계 노드)**: Linux(VPS) 2대 이상 구성이 가장 일반적.
- **혼합 토폴로지 예시**: `iOS(클라이언트) → Linux Relay-1(AWG) → Linux Relay-2(Egress)`.

#### 플랫폼별 주의점

- **iOS**: 백그라운드 정책으로 재연결 지연이 생길 수 있어 On-Demand 규칙 권장.
- **Android**: Always-on VPN + "VPN 없이 연결 차단" 옵션으로 누수 방지 강화.
- **Windows/macOS**: 슬립/절전 복귀 시 라우팅 재적용(킬스위치 유지) 점검 필요.
- **Linux**: `systemd` 자동복구 + 방화벽 기본차단 정책과 함께 운영 권장.

#### 빠른 적용 순서 (플랫폼 공통)

1. 클라이언트별 AWG 프로필 배포(키/피어 분리).
2. Relay-1/Relay-2 라우팅 및 NAT 정책 분리.
3. DNS/IPv6/킬스위치 정책을 플랫폼별로 동일 수준으로 맞춤.
4. 실제 접속 테스트(IPv4/IPv6/DNS leak + 터널 단절 복구) 수행.

### 크로스플랫폼 고려 시 기술스택 추천

아래 조합이 운영 난이도/유지보수/우회 유연성 균형이 좋습니다.

#### 1) 권장 기본 스택 (Recommended)

- **터널/난독화**: AmneziaWG
- **서버 OS**: Ubuntu LTS (Relay-1, Relay-2 공통)
- **자동화**: Ansible (노드 공통 설정/재배포)
- **방화벽**: nftables 또는 UFW(내부적으로 nftables)
- **관측성**: Prometheus + Grafana + Loki(최소 로그 원칙)
- **비밀관리**: SOPS + age 또는 1Password/Bitwarden Secrets

#### 2) 클라이언트 플랫폼별 권장 조합

- **iOS / Android**: Amnezia 앱 + Always-on(안드로이드) / On-Demand(iOS)
- **Windows / macOS**: Amnezia 클라이언트 + 부팅 시 자동 연결 + 절전 복귀 후 재확인 스크립트
- **Linux Desktop/Server**: `systemd` 서비스로 터널 자동 복구 + DNS 강제

#### 3) 배포 패턴 권장

1. **IaC + 구성관리 분리**: (선택) Terraform로 VPS 프로비저닝, Ansible로 VPN 설정.
2. **환경 분리**: `dev/stage/prod` 키·피어·egress 풀 분리.
3. **릴리즈 전략**: Relay-2(egress)부터 점진 배포 후 Relay-1 반영.
4. **검증 자동화**: 배포 후 `DNS leak`, `IPv6 leak`, `Kill switch` 테스트를 CI 잡으로 실행.

#### 4) 왜 이 스택을 추천하나?

- 모바일/데스크톱/서버 모두 동일 운영모델로 맞추기 쉽고,
- 장애 시 노드 교체/키 교체/경로 변경을 자동화하기 좋으며,
- 우회 정책(다단/로테이션/프로토콜 변경)을 코드로 관리하기 쉽기 때문입니다.

### 한 줄 결론

- **Obfuscation은 "VPN 사용 사실 은닉"에 도움**이 되지만,
- **IP 비노출 보장은 네트워크 토폴로지(다단 중계/egress 분리)로 달성**해야 합니다.
- **최대 우회 목적이라면 단일 노드보다 다단·다사업자·로테이션 운영이 핵심**입니다.
- **오픈 VPN은 임시 우회 용도까지만**, 실사용은 직접 통제 인프라가 안전합니다.
